# Porting Knowledge

## Windowing and input

- In the SDL/bgfx path, `BgfxRenderer::Init` already knows the real drawable size, but the bgfx-backed `DX8Wrapper` used to seed `Render2DClass::ScreenResolution` before copying that size back out of the renderer. The fix is to pull the device resolution immediately after renderer init and to refresh `Render2DClass::Set_Screen_Resolution` on every later `Set_Render_Device` / `Set_Device_Resolution` call.
- SDL window resize handling needs to use drawable pixel size, not just logical window size. `SDL_EVENT_WINDOW_RESIZED` is not sufficient on its own for high-DPI/X11 cases; handle `SDL_EVENT_WINDOW_PIXEL_SIZE_CHANGED` (and platform-specific drawable resize events such as Metal view resize) and push the resulting pixel dimensions through `WW3D::Set_Device_Resolution`.
- In the bgfx port, `Get_Device_Resolution` must report the real window/backbuffer size (`Width`/`Height`), not `ActiveWidth`/`ActiveHeight`. The latter tracks the currently bound render target, so using it for window synchronization makes resize logic depend on whether an offscreen target happened to be active.
- SDL resize resync must cover more than explicit drag-resize events. Maximize/restore, fullscreen enter/leave, display/DPI changes, and cross-monitor moves can all change the drawable size or windowed/fullscreen state without going through the same simple event sequence, so the window bridge should funnel all of those cases through the same renderer resync path.
- DirectInput acquisition and SDL relative mouse mode should stay separate in the port. The game still wants SDL event watches and cursor tracking while focused, but relative mode should only be active in shooter gameplay. Tying relative mode directly to `Acquire()` keeps menus/loading screens trapped in relative mouse mode.
- The current "shooter mode" rule is derived from existing engine state rather than new flags: relative mode/gameplay capture is enabled only when `Input` is not in menu mode, not in console mode, and `CombatManager` is not reporting a threaded level load in progress.
- When leaving relative mouse mode, restore the cursor by warping the SDL pointer back to the engine's current render-space cursor position converted into window coordinates. Without that handoff, menu entry after gameplay can leave the cursor at SDL's last relative-mode location instead of where the game/UI expects it to be.

## UI / dialogs / HUD

- The engine already has the correct authored-UI model: `StyleMgrClass::Get_Layout_Rect()` computes a centered 4:3 safe area inside the current screen. WWUI dialogs use that rect during layout/reflow, so resize/aspect bugs usually come from code outside the dialog system bypassing it and anchoring directly to the raw framebuffer.
- Preserving the original UI on modern displays means preserving that 4:3 composition, not stretching authored overlays to every window edge. HUD/loading/scope elements that were authored as 640x480-era edge anchors should generally be projected into the centered layout rect, while true screen-center effects and world-projected markers should only move if they depended on stale screen metrics.
- `Render2DClass` stores screen-space conversion state in two places: the shared static `ScreenResolution`, and each renderer's own coordinate range. Live resize only works if both stay in sync. Updating the device/backbuffer size without also calling `Render2DClass::Set_Screen_Resolution(...)` leaves dialogs/HUD code rendering against stale dimensions.
- `Render2DClass` also bakes logical coordinates into vertices when quads are built, not only when they are drawn. Renderers that call `Set_Coordinate_Range(Render2DClass::Get_Screen_Resolution())` and then rebuild frequently can auto-follow resize by refreshing that range, but baked one-time geometry must be explicitly rebuilt when the layout rect changes.
- HUD and loading-screen font refresh is a two-step process. `StyleMgrClass::Refresh_Fonts()` rebuilds the shared font resources, but any long-lived sentence/font renderer that cached a specific font pointer may need that binding reapplied after the refresh.
- The centered 4:3 layout rect is **not** the right anchor space for every UI layer. It matches authored dialog/backdrop/video framing, but portrait/tall-window HUD widgets that are supposed to sit in the real screen corners should still anchor to `Render2DClass::Get_Screen_Resolution()` and keep only their sizing/fonts tied to the 4:3-authored scale.
- `MapCtrlClass` has a separate scaling trap from the rest of WWUI: its `Zoom` and `ScrollPos` live in map-texture texels, but its control rect is in screen pixels. If viewport size is derived directly from the current `Rect.Width()/Height()`, higher resolutions reveal more of the map instead of scaling the authored EVA panel up. The correct model is to multiply screen-space map zoom/pan by the current WWUI resolution scale so the visible map extents stay tied to the control's authored size while the rendered panel grows with resolution.
- The stb font port currently has an important distinction to preserve: glyph bitmap storage width is not the same thing as text advance. If padded glyph atlas cell width is reused as the advance, sentence extents drift and menu/loading text becomes slightly misaligned even when the authored coordinates are correct. Transparent glyph blits also need to skip zero-alpha texels so right-overhang characters can overlap safely without erasing previously drawn glyphs.
- Bink movie playback needs the same 4:3 presentation rule as menu/loading backdrops. Even though the decode/upload path is modernized, the final presentation quad should still be submitted against a centered 4:3 display rect rather than stretched across the full window.

## Bink movie playback

- Renegade's game-side movie code only needs a narrow RAD-style surface (`BinkOpen`, `BinkDoFrame`, `BinkNextFrame`, `BinkCopyToBuffer`, `BinkWait`, `BinkClose`, `BinkSoundUseDirectSound` plus a few public `BINK` fields). Keeping that seam intact is the least invasive way to replace the missing SDK/runtime.
- The vendored FFmpeg 8.1 Bink support is a good reference source, but it is not practical to link wholesale just for startup movies. The workable approach here is to extract/port the needed Bink 1 container, video, audio, tables, and DSP logic into `Code/BinkMovie` and keep the rest of Renegade unaware of FFmpeg.
- FFmpeg's `libavcodec/bink.c` is built with `BITSTREAM_READER_LE`, so the legacy Bink video bitstream should be read little-endian. Misreading it as MSB-first corrupts bundle counts and block parsing almost immediately. `binkaudio.c` is also little-endian.
- Bink bundle decode state must preserve the distinction between `cur_dec == nullptr` (no more entries in this bundle chunk) and `cur_dec > cur_ptr` (decoded-but-not-yet-consumed entries remain buffered). Treating both as plain `count == 0` makes decode fail on the next block row.
- Local movie frame planes need padding beyond the visible width/height. FFmpeg frame buffers have enough slack for legal 16x16 Bink edge blocks; an exact `width * height` allocation will overflow on bottom/right edge scaled/fill blocks even for valid streams such as `EA_WW.BIK`.
- The old DX8-era movie upload assumptions are not safe on Linux/bgfx. The path must not write through stale DX8 texture internals, and it must not assume that CPU-side surface edits automatically refresh GPU textures.
- The Bink audio path is performance-sensitive: Renegade's startup movies use the FFmpeg `binkaudio_rdft` path, and a naive inverse DFT makes decode time explode into hundreds of milliseconds per frame. The in-tree decoder needs an iterative FFT-style inverse transform plus reused scratch buffers to keep audio decode in the low-millisecond range.
- `SurfaceClass::Unlock()` under the bgfx renderer only releases the CPU lock; it does not mark the owning texture dirty or push modified pixels back into bgfx. Reusing a texture by lock/write/unlock alone can therefore leave the old GPU contents on screen. Dynamic movie/video uploads should use explicit `bgfx::updateTexture2D` (or another explicit texture refresh path), not rely on surface unlock side effects.
- The current fast movie path is shader-driven: `BINKMovie.cpp` requests decoded Y/U/V planes through the local `BinkGetFramePlanes` extension, uploads luma/chroma textures directly (`R8`/`RG8` when supported, `RGBA8` fallback otherwise), and converts to RGB in `Code/ww3d2/shaders/fs_movie_yuv.sc`. This removes the CPU RGB565 conversion cost and fixes the invisible-video regression from the earlier "reuse the same texture object" experiment.
- Movie file lookup must go through `_TheFileFactory`, not direct `std::ifstream`, `std::filesystem`, or Win32-style `GetFileAttributes` checks. The engine file factory already carries the correct base-directory search behavior and Linux case-insensitive path resolution, which is required for paths such as `DATA\\MOVIES\\R_INTRO.BIK` to resolve to `Data/Movies/R_Intro.BIK`.

## Shadow mapping

- In the bgfx renderer, fixed-function draws only auto-receive CSM when the shader destination blend is `DSTBLEND_ZERO`.
- The tank-track slope regression was caused by fixed-function mesh passes and sorted draws dropping explicit `receive_shadows` / `cast_shadows` intent before bgfx submission and falling back to that opaque-only default.
- Sorted buffered draws need the same explicit shadow-flag propagation as immediate draws because the later flush path otherwise reclassifies them with the default heuristic and can repaint already-shadowed terrain as lit.
- bgfx shader custom commands in the current CMake setup do not track included `.sh` files as dependencies, so edits under `Code/ww3d2/shaders/*.sh` require touching the dependent `.sc` files or otherwise forcing a shader rebuild.
- In the CSM light view used by `shadowmap.cpp`, casters that sit toward the sun/light-camera side of the receiver slice produce **larger** light-space Z values, so behind-camera caster coverage must expand `max_z` (reducing `z_near`) rather than only pushing `min_z` farther away. Extending the wrong side looks like a gradual receiver cutoff instead of a clean caster pop because the shadow gets clipped by the cascade near plane as the camera moves past the caster.
- The old projected-shadow runtime lived under `wwphys` as a separate system from bgfx shadow maps: `DynamicShadowManagerClass` generated per-object render-to-texture projectors, and static anim shadow projectors generated cached textures that projected onto dynamic units. Removing those paths requires clearing both the object-level managers and the `PhysicsSceneClass` static-shadow generation/config glue.
- `Shadow_Mode` still exists for compatibility with saved settings and UI code, but the runtime should treat every non-zero legacy value as the modern shadow-map mode. This prevents old blob/projection settings from re-enabling deleted shadow projector code while keeping registry migration simple.
- `PhysClass::Get_Static_Lighting_Environment` originally used `IS_IN_THE_SUN` as a coarse mesh-level occlusion test: it raycast the mesh center toward the sun, then passed that boolean into `PhysicsSceneClass::Compute_Static_Lighting` to decide whether the sun light entered the cached light environment at all. With bgfx CSM enabled, that whole-mesh gating is wrong because it darkens the entire mesh before per-pixel shadowing runs; static lighting should always include the enabled sun and let the shadow map handle occlusion.

## Texture loading

- Weapon definitions can carry two different icon sources, but the legacy data is not always trustworthy: some `HUDIconTextureName` entries still point at dead `hud_6x4_weapon_*.tga` assets while the usable shipped art is only reachable through `IconTextureName` (often as a `.dds`). For in-game HUD rendering, prefer the first icon asset that actually exists instead of blindly trusting one field.
- `Render2DClass` callers often normalize UVs immediately after `Set_Texture`. If a first-use UI/HUD texture has no thumbnail metadata, `TextureClass::Width/Height` stay `0` until the lazy load runs; foreground-load those 2D textures on the render thread before code bakes UVs, or you can end up with repeating fallback/missing-texture patterns that "fix themselves" only after another menu/UI flow rebuilds the quad.
- `BitmapHandlerClass::Copy_Image` has a special bumpmap conversion path for `WW3D_FORMAT_U8V8`, `WW3D_FORMAT_L6V5U5`, and `WW3D_FORMAT_X8L8V8U8` that derives gradients from neighboring source texels. That path must clamp both horizontal and vertical neighbor lookups at the image edges; raw `src_ptr +/- src_bpp` arithmetic on the first or last column will underflow/overflow 24-bit TGA image buffers during level texture loads.
- The crash signature for this bug is an ASan heap-buffer-overflow in `BitmapHandlerClass::Read_B8G8R8A8` while loading an uncompressed mipmap from `TextureLoadTaskClass::Load_Uncompressed_Mipmap`, usually with the invalid address a few bytes before the `Targa::Load` allocation.
- Mission map textures are a lazy-load edge case: `TextureClass::Get_Texture()` can return a texture whose `Get_Width()` / `Get_Height()` are still `0` until `Init()` runs if no thumbnail entry exists for that asset. `MapMgrClass::Set_Map_Texture` and `MapCtrlClass::Set_Map_Texture` both need real dimensions immediately; otherwise gameplay shroud reveal keeps early-returning on a `0x0` map and the EVA Data Link map shows up fully black.
- EVA menu maps also rely on correct map-space scroll clamping. `MapCtrlClass::ScrollPos` is stored in texture/map texels, so the valid range is based on the zoomed visible window (`Rect / Zoom`) and half of the remaining map extents. Clamping against the full texture size lets the view center drift into padded DDS border pixels, which can make a valid map texture appear as a mostly black panel with only markers/icons still visible.
- D3D's packed 16-bit alpha formats are **not** byte-compatible with bgfx's similarly named packed formats. In particular, direct-copying `A1R5G5B5` / `X1R5G5B5` into bgfx `BGR5A1`, or `A4R4G4B4` / `X4R4G4B4` into bgfx `BGRA4`, scrambles the authored channels. For bgfx texture uploads, these formats should go through the existing `Convert_Surface_Copy_To_BGRA8` path unless/until a proven bit-exact repack exists.
- `WW3D_FORMAT_R5G6B5` also needs caution in the bgfx port. The main-menu backdrop regression showed that Renegade's 16-bit UI/menu textures can render with swapped-looking color channels when direct-uploaded as native bgfx `R5G6B5`; converting them through the 32-bit upload path preserves the authored red/orange output.
- Legacy runtime texture support in the bgfx port should be based on the actual upload path, not just native source-format support. Many Renegade formats (`R5G6B5`, `A4R4G4B4`, `U8V8`, etc.) are intentionally converted on the CPU into `BGRA8` before upload, so treating them as unsupported in `DX8Caps` / `Get_Valid_Texture_Format` can trigger false "No valid texture format found" asserts during normal background loads even though texture creation would succeed.
- The M01 shoreline regression reported with `savegame04.sav` was **not** a missing asset lookup. The real water pass uses `water_texture.tga`, `water_foam.tga`, and the `bump_water.tga` / `water_reflect.tga` bump-env layer.
- In the bgfx port, `Resolve_Texture_Handle` needs to be careful with lazy texture loading: returning the white fallback immediately for a texture that is merely "not initialized yet" can turn valid world textures into persistent-looking white geometry at level start. For world-critical textures, the first bind needs to force the pending load to complete rather than render white and hope the background loader catches up later.
- `SurfaceClass::PixelSize` / `CreateCopy` must understand the legacy bump formats too, not just the common color formats. If `WW3D_FORMAT_U8V8`, `WW3D_FORMAT_L6V5U5`, or `WW3D_FORMAT_X8L8V8U8` report `0` bytes per pixel, bgfx texture creation silently fails and the renderer falls back to the white texture.
- Renegade's COUNT2 texture mappers treat passthrough UVs as having an implicit third component of `1`, not `0`. The classic mappers in `mapper.cpp` write scroll/frame offsets into `Matrix3D::m[0].Z` / `m[1].Z`, so the bgfx texgen vertex shader must feed passthrough UV transforms with `(u, v, 1, 1)` or those offsets disappear.
- A null fixed-function texture stage is **not** the same thing as an unresolved texture asset. In the shoreline foam pass, stage 1 uses `D3DTOP_ADD` with no bound texture; binding bgfx's white fallback there turns the combiner into `current + white` and produces the giant solid-white shore polygon. Keep the white fallback for real asset-load failures, but use a neutral black texture for genuinely null stage bindings.

## First-person weapon animation lookup

- `StringClass` must be explicitly cast to `const char *` before being passed through `%s` varargs formatters like `StringClass::Format` or `Debug_Say`. C++ will apply implicit conversions for normal function parameters, but not for `...`, and the resulting corrupted strings can look like random asset names instead of valid HAnim identifiers.
- `Code/Combat/weaponview.cpp` builds first-person weapon, hand, and bob animation names via formatted strings. If those `StringClass` values are passed to `%s` without casts, idle/default visuals may still appear while state-driven first-person animations such as reload/fire/enter/exit fail to resolve.
- The same varargs rule applies to renderer/debug logging. Passing `Texture->Get_Full_Path()` or savegame `MapFilename` directly to `%s` can produce garbage names in logs on 64-bit builds even when the underlying asset loads correctly. Use `Peek_Buffer()` (or an explicit `const char *` cast) at the call site.
- The same failure mode also hits variadic helpers that take the *format string* itself, not just `%s` arguments. `cDiagnostics::Add_Diagnostic(LPCSTR format, ...)` will misbehave if a `StringClass` is passed as the first argument, because the object is forwarded through `va_start`/`vsprintf` instead of its character buffer. Packet stats had both forms at once: `WWDEBUG_SAY("%s", StringClass)` in `apppacketstats.cpp` and `Add_Diagnostic(StringClass)` in `diagnostics.cpp`.
- Adding `printf`-style format attributes to the shared narrow-string debug wrappers (`WWDebug_Printf`, `WWLib_Debug_Printf*`) and to `StringClass::Format` is a practical guardrail on GCC/Clang builds. It does not change runtime behavior, but it lets the compiler diagnose future object-through-varargs callsites during normal builds instead of leaving them to show up later as random garbled strings.

## Menu/dialog behavior

- The lightweight client menu replacements in `menu_dialog_subset.cpp` should only disable features that are truly unsupported. Disabling `IDC_MENU_LOAD_SP_GAME_BUTTON` there blocks the main-menu load path even though the standard `LoadSPGameMenuClass` flow still works.
- `GameInitMgrClass::Continue_Game` sits on the hot path for closing the in-mission EVA/menu dialogs. The original `PRE_SERVICE_TIME` busy-wait was specific to the legacy sound-page swap behavior; on the SDL backend it translates directly into visible resume latency.
- `DlgMsgBox` notifies observers with `Yes` / `No` **before** the popup actually closes, then sends `Quitting` from `End_Dialog()`. Menu flows that tear down other dialogs or change game modes should defer that work until `Quitting` to avoid mutating the dialog stack while the confirmation popup is still active.

## Mesh shader and material pipeline

- **D3DRS_COLORVERTEX is always TRUE**: Set in `DX8Wrapper::Init` and `bgfxdynamicbuffer.cpp`, never set to FALSE anywhere in the codebase. This means color source resolution can query `VertexMaterialClass::Get_*_Color_Source()` directly instead of going through D3D render state.
- **Specular is effectively unused**: Loaded/stored by `VertexMaterialClass` but never rendered. All consumers set `ShaderClass::SECONDARY_GRADIENT_DISABLE`. No need to implement specular in the shader pipeline.
- **Max 2 texture stages confirmed**: `MAX_TEXTURE_STAGES=2` throughout the codebase. No consumer uses more than 2 stages.
- **Material color sources**: `VertexMaterialClass` exposes `Get_Diffuse_Color_Source()`, `Get_Ambient_Color_Source()`, `Get_Emissive_Color_Source()` returning `MATERIAL` (0), `COLOR1` (1), or `COLOR2` (2). In practice only `MATERIAL` and `COLOR1` are used.
- **LightEnvironmentClass CPU reduction**: Reduces arbitrary scene lights to max 4 directional lights + ambient on CPU. This stays as-is; the shader receives 4 directional lights via uniform arrays.
- **FVF has_normals determines lighting mode**: Meshes in a DX8TextureCategoryClass share the same FVF. `(FVF & VERTEX_FORMAT_FLAG_NORMAL) != 0` determines whether full N·L lighting or emissive-only mode is used.
- **Texgen determination at classification time**: Whether a mesh needs texgen is determined by checking `VertexMaterialClass::Peek_Mapper(stage)` for non-null mappers, not by querying live DX8 texture stage state. This allows the program choice to be pre-computed.
- **bgfx uniforms are sticky until changed**: Uniform values persist across submit calls within a frame. Lighting uniforms must always be set before every mesh submit since different meshes have different light environments.

## DX8 Bump Environment Mapping (EMBM)

- **Not tangent-space normal mapping**: W3D mesh format has NO tangent/binormal vertex data. The original D3D8 renderer used the fixed-function `D3DTOP_BUMPENVMAP` operation, which is UV perturbation — NOT modern tangent-space normal mapping.
- **Bump texture formats**: `WW3D_FORMAT_U8V8` (2 bytes: signed U, signed V), `WW3D_FORMAT_L6V5U5` (2 bytes: packed signed U5, signed V5, unsigned L6), `WW3D_FORMAT_X8L8V8U8` (4 bytes: signed U, signed V, unsigned L, padding X). All converted to BGRA8 for bgfx.
- **Signed-to-unsigned bias**: U and V channels are signed bytes (-128 to 127). XOR with 0x80 converts to unsigned [0,255] for storage. Shader decodes via `val * 2.0 - 1.0` to recover [-1,1] range. Luminance (L) channel is unsigned, stored directly in alpha.
- **BumpEnvTextureMapperClass**: Extends LinearOffsetTextureMapperClass. Animates a rotation angle (`CurrentAngle += RadiansPerSecond * delta`), computes a 2×2 rotation/scale matrix, and stores it in DX8Wrapper texture stage state via `D3DTSS_BUMPENVMAT00/01/10/11`.
- **Bump matrix is dynamic per-draw**: Read from `DX8Wrapper::TextureStageStates[stage][D3DTSS_BUMPENVMAT*]` at submit time. Values stored as float-as-DWORD via `F2DW()`, decoded back with `memcpy`.
- **Stage 0 is a passthrough**: The bump stage doesn't produce color output — it only perturbs the UV coordinates of the next stage. Stage 0 alpha op is DISABLE per D3D8 spec.
- **Three gradient types**: `GRADIENT_BUMPENVMAP` (UV perturbation only), `GRADIENT_BUMPENVMAPLUMINANCE` (+ luminance modulation from alpha channel), `GRADIENT_DOTPRODUCT3` (dot product between bias-decoded texture and current color).
- **Real runtime users are file-driven, not game-specific C++ effects**: the original bump path is primarily `meshmdlio.cpp` -> `VertexMaterialClass::Load_W3D()` -> `BumpEnvTextureMapperClass` / bump shader gradients / `W3DTEXTURE_TYPE_BUMPMAP`. I did not find a distinct Renegade gameplay-side hardcoded EMBM factory beyond skeleton/test code.
- **Preserve bump intent before renderer init**: load-time code can run before DX8/bgfx caps are fully initialized. If `meshmatdesc.cpp` kills bump passes or `texture.cpp` downgrades bump textures during that phase, authored bump materials are lost permanently for the session. The bgfx port should preserve those authored bump materials until actual runtime caps are known.
- **BUMPENVMAPLUMINANCE state layout**: this codebase initializes `D3DTSS_BUMPENVMAT*` on stage 0, but `D3DTSS_BUMPENVLSCALE/LOFFSET` on stage 1 (`dx8wrapper.cpp`, `bgfxdynamicbuffer.cpp`). The bgfx uniform upload must mirror that layout for parity with original authored luminance users.
